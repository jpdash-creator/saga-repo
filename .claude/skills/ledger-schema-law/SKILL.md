## Area 1 — Entity Creation Thresholds

### 1.1 — Purpose

The entity creation thresholds define the minimum prose evidence required for C-38 [FORCE LEDGER AUDIT AND UPDATE] to trigger the creation of a new ledger file for a discovered entity. The thresholds are designed to prevent both premature ledger creation (for entities that are merely mentioned in passing) and late creation (for entities that have been canonically established but lack ledger coverage).

### 1.2 — Character Entity Thresholds

**Threshold C-1 — Side Character Ledger Creation.**
A named character becomes ledger-eligible when: a named character appears in any Area with any combination of the following — direct action, spoken dialogue, physical description, or narrative attention from the POV character. A character who is named and present in the scene, even without dialogue, meets this threshold. A character mentioned by name but not present in any Area does NOT meet this threshold and is not ledger-eligible until they appear directly. Which artifact a ledger-eligible character receives is routed by their Part 19 Depth Spectrum tier (Part 19 Rule 19.6.1.1 is the tier authority): a **Tier A** character and a **Tier B** character each receive a full `ledger-character-side/[name].md` file on the Area 2.1 template, the Ledger Type reading Tier A or Tier B, with a registry row in `ledger-character-side/_index.md` that points at the file; a **Tier C** character that acts or speaks must have an abbreviated `_index.md` entry carrying its Part 39 behavioral line by the end of Gate 2 (Part 39 Rule 39.4.3.1): the entry is made before drafting when the Chapter Spec names the person, and at Gate 2 from what the prose established, the gaps marked `OPEN-AREA`, when the drafting agent improvised the person in the prose; one merely named in passing need not; a **Tier D** character receives a row on the Tier D template of Area 2.11 in the same `_index.md`, and no file (Part 19 Rule 19.1.2.7). Tier routing defers to Part 19 Rule 19.6.1.1, which requires a Side Character Profile, kept as a full file, for Tier A and Tier B characters and states that Tier C characters are not required to have formal profiles. Promotion to Tier B or Tier A under Part 19 Rule 19.9.2.1 (Tier Transitions Are Permitted) is the moment the full file is created from a registry row — the existing `_index.md` entry is migrated into Section 1 and the registry row replaced by a pointer to the new file; a promotion from Tier B to Tier A changes only the Ledger Type and the Section 9 tier field of the existing file.

**Threshold C-2 — Villain Classification.**
When a newly-introduced named character's first Area appearance contains any of the following qualifying behaviors — violence against, or in opposition to, a hero or their allies (training and sparring are not qualifying behaviors), deception, coercion, cruelty, faction-opposition to hero interests, cultivation suppression, or betrayal — C-38 must fire an `AskUserQuestion` before creating their ledger file, asking whether the character should be classified as Villain (ledger-character-villain/) rather than Side Character. This question fires once per character, only at first Area appearance, only when qualifying behavior is present. If the user confirms Villain classification, the file is created in `ledger-character-villain/` instead. **Two additions.** (1) **A non-sentient monster's attack, pursuit, hostility or killing is not qualifying behavior**, and this question is never put for a non-sentient monster (Part 40 Rule 40.12.2.1); a sentient monster is dealt with under Threshold M-3. (2) A Villain ruling names a depth tier only when the author maps one (Part 18 Area 6.3, Rule 18.6.3.3); an agent never names one. Until the author maps a tier, the villain's tier reads UNMAPPED and this threshold works as it always did: the file is created in `ledger-character-villain/` on the Area 2.2 template and the villain is registered in full. Where the author maps a tier, the artifact follows it: a Tier A or Tier B villain a full `ledger-character-villain/[name].md` file on the Area 2.2 template; a Tier C side villain an abbreviated entry and a Tier D side villain a row, both in `ledger-character-villain/_index.md` on the Area 2.11 schemas.

**Threshold C-3 — Hero Ledger (Manual Only).**
Hero ledger files (`ledger-character-hero/[name].md`) are never auto-created by C-38. Hero status is user-designated. C-38 may flag a Side Character as a potential Hero candidate for user consideration if their weight across multiple Areas clearly warrants it, but it does not act unilaterally. The flag text is: `⚠ Hero designation consideration: [name] has appeared in [N] Areas with significant protagonist-level narrative weight. User may wish to promote to Hero ledger via explicit instruction.`

**Threshold M-1 — Monster Kind Registration.**
A new Kind row in `ledger-character-monster/_index.md` must be made when: a confirmed and written Area first describes a kind of monster (Part 40 Rule 40.1.1.1) by any physical, behavioural or habitat feature, or the author sets the Kind in an interview. The row is made by the Post-Write Ledger Update of that Area and never before it; a Kind named only in a spec, or in a draft discarded by `[SKIP WRITE]`, meets nothing (Part 38 Rule 1.3.2), except that a Kind to which a Tier C or Tier D Individual named by a Chapter Spec points receives its row in the same pass as that Individual (Threshold M-2). A Kind carries a depth tier A to D in its registry row (Part 40 Rule 40.6.1.4), and, whatever its tier, it receives a file of its own on the Area 3.10 Kind form at its first Named Move, when it recurs at Section scale, or when it is a sentient Kind; a Tier A or Tier B Kind has a file by its tier. An ordinary animal is not a monster and meets nothing (Part 40 Rule 40.1.1.2). There is no count.

**Threshold M-2 — Monster Individual.**
An Individual entry must be made when: a monster has a proper name, acts with story consequence, speaks, or is named by a Chapter Spec. It receives an entry at the tier the story gives it (Part 40 Area 6): a Tier A or Tier B Individual a full file on the Area 3.10 template, with a registry row that points at the file; a Tier C Individual an abbreviated entry in `ledger-character-monster/_index.md`; a Tier D Individual one row in the same `_index.md`. Tier A and Tier B Individuals and every sentient monster are built by hand with the author before they appear (`/new-character <name> monster`); a Tier C or Tier D monster that a Chapter Spec names is registered before drafting, and one the drafting agent improvises in the Area is registered at Gate 2 from what the Area established, every field it did not settle marked `OPEN-AREA`. A pack that the Area treats as one body is carried by its Kind and, where it acts with consequence, by one Individual entry that names the pack. There is no count.

**Threshold M-3 — Sentient Monster Classification.**
A sentient monster (Part 40 Area 11) whose first Area appearance shows ideology-driven opposition to a hero or their allies raises the same `AskUserQuestion` as Threshold C-2: whether it is classified Villain (the record then moves to `ledger-character-villain/`, Part 40 Rule 40.12.3.1) or stays a monster. The question fires once. A non-sentient monster never raises it.

### 1.3 — World and Location Entity Thresholds

**Threshold L-1 — Location Ledger Creation.**
A new `ledger-worlds-location/[name].md` file must be created when: a named place receives any physical, sensory, or spatial description in any Area. A location mentioned by name but not described does NOT meet this threshold. A location named and described (even in one sentence) meets this threshold.

**Threshold L-2 — Kingdom-State Ledger Creation.**
A new `ledger-worlds-kingdom-state/[name].md` file (or equivalent kingdom-state folder) must be created when: any named kingdom, empire, polity, city-state, sect-territory, or governing entity is mentioned by name in any Area. Mention by name alone (without physical description) is sufficient for kingdom-state threshold — kingdoms are politically significant even when not physically described.

### 1.4 — People and Society Entity Thresholds

**Threshold F-1 — Faction Ledger Creation.**
Any named organization, sect, guild, alliance, military unit, political bloc, or formal association that is mentioned by name and whose existence is confirmed (not merely speculated about) in prose is recorded on one of two tiers. **Tier F-B** is an abbreviated registry entry on the Area 2.11 schema, in `ledger-people-society-faction/_index.md`; a named group stays at Tier F-B until its first on-page action. A new `ledger-people-society-faction/[name].md` file, on the Area 2.6 template, must be created at the group's first on-page action, or earlier when governance detail is needed, and the Tier F-B entry is then replaced by a pointer to the file.

**Author-directed faction file.** The author may direct creation of a faction file before its first Area; it records First Area Appearance as not yet established and satisfies Threshold F-1.

**Threshold V-1 — Civilization Ledger Creation.**
A new `ledger-people-society-civilization/[name].md` file must be created when: a named civilization, cultural identity, or species-group is described with any cultural, historical, or civilizational characteristic in prose. A single kingdom's or sect's own culture stays in its faction and location ledgers; a civilization file is created only for a culture spanning several polities or a species.

### 1.5 — Object Entity Thresholds

**Threshold O-1 — Relic/Artifact Ledger Creation.**
A new `ledger-energy-relics-artifacts/[name].md` file must be created when: a named relic, artifact, or formation array is described in active use or detailed characterization in any Area. Passive mention by name without description does not meet this threshold.

**Threshold O-2 — Weapon Ledger Creation.**
A new `ledger-technology-weapon/[name].md` file must be created when: a named weapon is described in active use in any Area. A weapon referenced by name but not used in the prose does not meet this threshold.

**Threshold O-3 — Vehicle Ledger Creation.**
A new `ledger-technology-vehicle/[name].md` file must be created when: a named vehicle is described in active use or detailed physical characterization in any Area.

**Threshold O-4 — Named-Item Register Entry.**
A new row in `ledger-named-items/_index.md` must be made when: a named item, as defined in Part 28 Rule 20.8.1, is written into a confirmed and written Area. There is no further test: a name that appears once, or only in speech, meets this threshold. The row is made by the Post-Write Ledger Update of that Area and never before it; a name that appears only in a spec, or in a draft discarded by `[SKIP WRITE]`, meets nothing (Part 38 Rule 1.3.2). The row is the item's whole ledger record unless the item also meets a threshold of its own (O-2 for a named weapon, O-3 for a named vehicle, or a threshold of Area 3); in that case the row points at the home entry and the home entry owns every descriptive fact. A Named Relic, Named Artifact, formation array or energy resource cache is a named item (Part 28 Rule 20.8.1; Part 12 Rule 2.2.3): it gets a row here, with the Type relic or artifact, formation array or energy cache, and its home entry stays under Threshold O-1, which is not changed. A named document, and a named agreement, treaty or accord, are not entered in this register; they are entered in `ledger-society-information` (Area 3.4; Part 28 Rule 20.8.7).

**Threshold O-5 — Named-Move Register Entry.**
A new row in `ledger-named-moves/_index.md` must be made when: a Named Move, Named Technique or Named Cultivation Practice (Part 2 Rule 3.2.1; Part 6 Rule 6.5.1) is written into a confirmed and written Area, or is set in a ledger by the author in a `/new-character` or `/update-ledger` pass. There is no further test: a move named once meets this threshold. The row is made by the same Post-Write Ledger Update, in the same pass in which the move is entered in the user's character-ledger entry (or the species, faction or school entry), and each points at the other (Part 6 Rule 6.5.2). A move named only in a spec, or in a draft discarded by `[SKIP WRITE]`, meets nothing (Part 38 Rule 1.3.2). The row is a pointer: the user's entry owns every value of the move. This threshold is separate from O-4 because a Named Move is not a named item (Part 28 Rule 20.8.1(b)).

**Threshold O-6 — Manual Ledger Entry.**
A manual-borne move or a manual title is entered in the generic register or the named-item register when an Area first writes it and is confirmed and written (Part 42 Rule 42.12.5.1); the Manual Ledger rows exist from the author's directive and need no prose.

### 1.5a — Calendar Entity Threshold

**Threshold D-1 — Dated Area Recorded in the Calendar Ledger.**
A row of `ledger-worlds-calendar/_index.md` must be made when: an Area is confirmed and written. The ledger is one file that exists from the start with its Baseline tables filled, so this threshold makes rows and never a file. The Post-Write Ledger Update of that Area, after `[CONFIRM WRITE]`, creates the Area row (First, Latest, Kind), rolls First and Latest up the Chapter, Novel-Part, Section and Phase rows (a `flashback` Area is left out of the rollups, because the story clock does not move at a flashback), and rewrites the Current Position row and the Total Entries line (Part 41 Area 9). The date recorded is the one that the Area's own date line states (Part 41 Area 5). There is no further test: every written Area is dated and none is exempt. The rows are made by that Post-Write Ledger Update and never before it; a date that appears only in a spec, or in a draft discarded by `[SKIP WRITE]`, meets nothing (Part 38 Rule 1.3.2). There is no count.

### 1.6 — New Entity Type Discovery

When C-38 identifies a named entity that does not fit any of the twenty-two established ledger types (the ten of Areas 2.1 to 2.10: Side Character, Villain, Hero, Location, Kingdom-State, Faction, Civilization, Relic/Artifact, Weapon, Vehicle; and the twelve of Areas 3.1 to 3.12: Travel, Distance, Affiliation Agreement, Information, Technology Scale, Technology Growth, Technology Science, Named-Item Register, Named-Move Register, Monster, Calendar, Manual), C-38 must:
1. Cross-reference Parts 1–41 to identify the governing Part for this entity type
2. Determine the correct ledger folder name using the `ledger-[domain]-[type]/` convention (the three shortened names `ledger-named-items/`, `ledger-named-moves/` and `ledger-society-information/`, are the author's exception)
3. Flag the new entity type in the C-38 preview as `NEW ENTITY TYPE — Part 37 schema not yet defined`
4. Request user direction before creating any file for this entity type
5. Once user confirms, add the schema to Part 37 as the next Area 3 subsection (Area 6) and create the ledger folder with `_index.md`

## Area 2 — Schema Templates

### 2.1 — Schema Template: Side Character Ledger

**File location:** `ledger-character-side/[name].md`
**Governing Canon Parts:** Parts 3, 4, 5, 6 (Area 12), 7, 8, 16, 17, 19, 20, 21, 22, 23, 26, 27, 31, 39
**Ledger Type:** Side Character

**Thirteen-section template.** Area 2.1 carries thirteen sections: Sections 1 to 10, Section 11 (Behavioral Signature) and Section 12 (Behavioral Evolution Log) under Part 39 (Character Behavioral Synthesis Law), and Section 13 (Current Condition, below). Every reference in this Part or elsewhere to the "10-Section Character Ledger Template" is read as the thirteen-section template.

**Section 13 — Current Condition.** Every character ledger also carries Section 13, Current Condition, placed after Section 12; Sections 1 to 12 keep their numbers. Section 13 records every state of the character as the story now stands, whoever or whatever caused the change: the emotional, mental, psychological, physical, metaphysical and soul states, and each wound or lasting mark with how long it lasts (a bruise heals in days, a cut hand after a battle is permanent, a soul wound is its own kind). A hero, a villain, a Tier A character and a Tier B character carry the detailed form shown at the end of the template below. A Tier C character and a Tier D person carry two lines in the Current Condition column of their registry row (Area 2.11). The Post-Write Ledger Update writes it after every Area that changes it, for every character the Area affects, and the Pre-Write Ledger Check reads it before every Area in which the character appears. A field with nothing recorded reads `none recorded at story start`.

**Tier scope of this template.** Area 2.1 is the full-file schema, and a full file belongs to a Tier A or a Tier B character (Threshold C-1, Area 1.2). Its `**Ledger Type:**` header field and its Section 9 `**Side Character Tier (Part 19):**` field read Tier A or Tier B, whichever the character holds, and are not offered as a choice with Tier C. A Tier C character may be registered on the Abbreviated Registry Entry schema of Area 2.11; a Tier D person is registered on the Tier D template of Area 2.11.

**Section 3 Innate Moves — required subsection.** Section 3 of the template below carries a mandatory `Innate Moves (Part 6 Area 12)` subsection, marked REQUIRED SUBSECTION in the template itself. It appears in every Side Character ledger file whether or not the character carries a species-innate move; where none is carried it is populated `(none registered)` rather than omitted. Part 37 governs this template.

**Section 3 Manual Kit — subsection (Part 42).** Section 3 of the template below carries a `Manual Kit (Part 42)` subsection after the `Signature Named Moves` and `Innate Moves` subsections, in the hero, villain and Tier A and Tier B side-character ledgers (the Villain and Hero templates of Areas 2.2 and 2.3 carry it through the shared Section 3). It is a pointer line to the Manual Ledger and holds no move block. For Varya and Aegon it reads `none` with a learning plan (Part 42 Area 15, Amendment 4), and the hero ledgers are frozen: the line is added to a hero ledger only on the author's permission.

### 2.11 — Schema Template: Abbreviated Registry Entry (`_index.md`)

**File location:** `ledger-[domain]-[type]/_index.md` — the per-folder registry of every folder in the Area 4 registry
**Governing Canon Parts:** the Area 2 schema of the folder whose registry it is; Part 19 for the Tier B/C/D routing of Threshold C-1 and Rule 19.1.2.7, Part 39 Section 3.5 for the Code cell; Area 5 for the B/L classification
**Creation threshold:** an entity that meets its Area 1 threshold receives a registry entry in its folder's `_index.md`. Where the entity also receives an entity file, the entry points at that file; where it does not — a Tier C side character that is registered at all, per Threshold C-1, a named group at Tier F-B, per Threshold F-1, and every Tier D person — the entry is the entity's whole ledger record.

---

**Purpose, and its limit.** A registry entry does four things and no more: it **identifies** the entity, **locates** it (in the prose record, and on disk), **classifies** it, and **points onward** to whatever holds the rest. It is a registry row, not a shadow ledger. Narrative, descriptive, lore, and event content that Areas 2.1–2.10 assign to a section of an entity file — or that another Part assigns to another ledger — is never restated in a registry entry; the entry points at it instead.

**Mandatory minimum columns.** Every per-entity registry row carries at least the six columns below, in this order, with the Area 5 Baseline/Living classification marked in the header row. A folder's registry MAY carry further columns where that folder's Area 2 schema supplies a classification value worth surfacing; it MUST NOT carry a column whose content the purpose limit above assigns elsewhere.

```markdown
| Entity Name (B) | Classification (B/L) | First Area Appearance (B) | Entity File (L) | Status (L) | Last Updated (L) |
|---|---|---|---|---|---|
| [canonical name as established in prose] | [the governing classification value from this folder's Area 2 schema — e.g. Side Character — Tier B (Part 19) — or "not yet established"] | [Area NN — Title (Ref: P.S.N.CCC.AA) — or "not yet established"] | [`[name].md` — or "none — this entry is the entity's whole ledger record"] | [Active — or the status established in prose] | [YYYY-MM-DD] |
```

**Field classification (Area 5).** `Entity Name` and `First Area Appearance` are Baseline (B) — established at creation from the introducing prose and locked thereafter absent a Canon Amendment. `Entity File`, `Status`, and `Last Updated` are Living (L) — updated after every Area that changes them. `Classification` is B/L on the same terms as the corresponding field in the folder's Area 2 schema. The Area 5 mandatory population rule applies unchanged: a column the introducing prose has established may not be left as "not yet established".

**Optional Aliases column.** Any folder's registry MAY carry a column `Aliases (B)`, added after the last column the registry already carries. It lists every other name, short form or spelling under which the entity appears in prose or in the ledgers (for example `Sol System` for Sol Star System), separated by semicolons, or `none`. Aliases identify the entity, which the purpose limit above allows. The column is filled at the entity's first appearance; a later alias is added to the cell and nothing already recorded is removed. ## Area 5 — Schema Field Classification

Every field in every schema template above is classified as one of two types:

**Baseline Information (B):** Established at entity creation and locked unless a Canon Amendment explicitly changes it. The initial establishment event is the Area that introduces the entity — fields populated at creation from that prose. Subsequent prose may enrich B fields that are "not yet established" but may not contradict B fields already established without a Canon Amendment.

**Living Information (L):** Updated after every relevant Area. The `[L — Updated at...]` notation in each section's footer defines the trigger condition for that section's Living fields.

**Part 39 Sections 11 and 12.** Section 11.2 (Signature Set), 11.3 (Contradiction and Cost) and 11.6 (Conditional Drift Map) are Baseline (B), except the "paid on the page at" field of 11.3, which is Living (L) because it is written when the cost is first rendered on the page (Part 39 Standard N39-13): a registered Signature moves only through a logged Section 12 drift event with a named trigger, never by editorial revision. Section 11.1's non-signature lines, 11.4, 11.4a, 11.5 and 11.7 are Living (L). Section 12 is Living and append-only. Unlike every other B field in this Part, a Part 39 Signature has a second lawful path to change besides Canon Amendment — the Part 39 Area 42 drift mechanism — and that second path is the whole purpose of the Section 11/12 pairing.

**Section 13.** Section 13 Current Condition, and the Current Condition column of a Tier C or Tier D registry row, are Living (L): the Post-Write Ledger Update writes them after every Area that changes a character's state, whoever caused the change.

**Monster entries.** In a Kind entry the depth tier, the stage band, the cultivation varieties, the habitat, the twelve trait lines, the distinct abilities and the Harvest line are Baseline (B) and change only by Canon Amendment. In an Individual entry the points where it differs from its Kind are Baseline (B), and its exact stage, current state, place, wounds, handler, grudges and Survival Status are Living (L). The Current Condition column of a Tier C or Tier D monster is Living (L), as for a person (Part 40 Area 5).

**Calendar ledger.** In `ledger-worlds-calendar/_index.md` the Epoch, Months, Weekdays, Fixed Days, Birth Years of the Eight Heroes and Planned Windows tables are Baseline (B): they mirror Part 41 and change only by Canon Amendment on the author's word (Part 41 Rule 41.1.3.4). One cell is the exception that enriches: a hero's Birthday cell reads `OPEN-AREA` until the author sets it or the first Area states it, and once set it stands as a Baseline value (Varya's and Aegon's are set; Part 41 Rule 41.8.1.2). The Planned Windows table carries no Status column and is wholly Baseline (Part 41 Rule 41.9.3.1). The Current Position row and every cell of the five recorded tables (Phase, Section, Novel-Part, Chapter, Area) are Living (L): the Post-Write Ledger Update writes them after every Area (Threshold D-1).

**Mandatory population rule:** Any field that the introducing prose has established must be populated at file creation. No field established in prose may be left as "not yet established" at creation time. "Not yet established" is reserved exclusively for fields where the introducing prose was genuinely silent.

**A field the template gains.** A field the template defines and the file lacks is added when the entity is next touched at Gate 2. The added field is written `OPEN-AREA` (`OPEN-AUTHOR` where only the author sets it), never an invented fact. No unfilled field blocks an Area. Only the eight heroes, the Section 1 side cast (the side-character files), and the Section 1 Spec locations and kingdom-state files are backfilled now; every other file gains the field when the entity is next touched at Gate 2.

**Open cells.** A field that is not yet set is written with one of two tokens, so that a writer can tell "I may fill this" from "I must ask". `OPEN-AREA` means prose may establish the value: the first Area that needs it sets it. `OPEN-AUTHOR` means only the author sets it: an agent that needs it asks the author and never invents a value. An open cell may carry a **Due by** note after its token, the Chapter or Area by which the story is expected to need the value, or `none set`. These wordings map to a token when their file is next touched: `not yet established` and `to be defined in prose` map to `OPEN-AREA`; `to be defined by author ruling`, `author will supply` and `AUTHOR-PENDING` map to `OPEN-AUTHOR`, even when joined to `not yet established`; `TBD` and `OPEN` map to the token that the field's own note names. In every template of this Part, `not yet established` inside a field's brackets reads as `OPEN-AREA` unless the field is one only the author sets. The tokens and the Due by note inform and never block a scene that the confirmed Chapter Spec requires; an `OPEN-AUTHOR` field that a scene needs, and a Due by that has passed, are raised to the author as a question. A cell of the Part 25 Area 29.2 table that is still empty follows Part 25 Rule 29.3.6 instead: prose may establish one small fact at a time, and a name goes to the author first.

**One owner for a fact held in two places.** Where one fact is held in two ledger places, one of them owns it and the other mirrors it. The entity file owns it over its `_index.md` row (the row points at the file; where they differ, the file stands). The character ledger owns it over any faction, location or kingdom list that mirrors it (Key Members, Known Characters Present, Members currently bound, and the like). A change is written to the owner first and the mirror follows from it. A mismatch between an owner and its mirror is surfaced at the next ALCA pass (`guardrails/audit/guardrail-alca.md`) as a finding for the author and is never resolved silently.

**Section 10 archive.** When a character ledger's Section 10 (Canon Events Log) passes 60 rows, the Post-Write Ledger Update moves the rows older than the current Section to an archive file in the character's own ledger folder, `_log/[name]-section-N.md` (for a hero, `ledger-character-hero/_log/[name]-section-N.md`, where N is the Section the rows belong to), and leaves one line in Section 10 that points at it. Section 12 is never archived: it stays append-only and whole. An archived row keeps its Area reference and stays citable, and the archive file is a ledger file like any other for ALCA. The 60 is a housekeeping figure: the move never delays or blocks an Area.
